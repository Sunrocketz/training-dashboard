# Architecture Decision Records (ADR)

Короткие записи «почему так». Новые решения — сверху (ниже шаблон). Не переписывать историю: устаревшие ADR помечать `Superseded`.

---

## ADR-012 — Составной рейтинг тренеров (TQI)

- **Дата:** 2026-08-01
- **Статус:** Accepted
- **Контекст:** Топ «лучших/требуют внимания» смотрел только на конверсию 1→5 и игнорировал mid-funnel, отсев и распад групп.
- **Решение:** Индекс **TQI** (`byTrainer.score`, 0–100): 45% conv1to5Weighted + 15% conv2 + 10% conv3 + 20% удержание (мало «ушли сами») + 5% контроль отказов + 5% стабильность (мало «распалась»). Веса и пороги (≥2 группы, ≥10 day1) в `metrics`. SoT формулы — GAS; UI повторяет при фильтре периода.
- **Последствия:** Порядок в топе может отличаться от чистой 1→5; веса можно крутить через `metrics` без смены полей.

## ADR-011 — «Распалась» в valid + метка; «не собралась» вне расчёта

- **Дата:** 2026-08-01
- **Статус:** Accepted
- **Контекст:** Счётчик групп у тренера расходился с листом: «распалась» исключалась из valid вместе с «не собралась», хотя старт и воронка уже были.
- **Решение:**
  - «не собралась» — по-прежнему вне valid (`notGathered`).
  - «распалась» — в valid, в totals/byTrainer/byMonth/воронку; флаг `groups[].fellApart`; счётчики и `fellApartConv1to5` / `fellApartShare`.
  - `schemaVersion: 3`, ключ кэша `dashboard_json_v3`.
  - UI: KPI «Распалось», бейдж, блоки аналитики по тренерам/месяцам, список групп в карточке тренера.
- **Последствия:** Число `totals.groups` и конверсии вырастут относительно v2 (туда войдут распавшиеся). Сравнивать периоды до/после выкладки осторожно.

## ADR-001 — Статический UI + Apps Script JSON API

- **Дата:** 2026-08-01
- **Статус:** Accepted
- **Контекст:** Нужен внешний дашборд поверх Google Sheets без тяжёлого backend.
- **Решение:** Данные агрегирует Apps Script; UI — статический `index.html` на Netlify; связь через публичный Web App `/exec`.
- **Последствия:** Простота и скорость; нет серверного auth; контракт JSON критичен; два пайплайна деплоя (git и clasp).

## ADR-002 — Единая функция агрегации

- **Дата:** 2026-08-01
- **Статус:** Accepted
- **Контекст:** Нужны и лист «Дашборд», и веб-JSON.
- **Решение:** `collectDashboardData()` — единственный расчёт; `buildDashboard` и `doGet` только потребители.
- **Последствия:** Менять формулы в одном месте; запрещено дублировать бизнес-логику в UI без причины.

## ADR-003 — Публичный доступ к `/exec` без ПДн учеников

- **Дата:** 2026-08-01
- **Статус:** Accepted
- **Контекст:** Web App с доступом «Anyone» упрощает fetch из статики.
- **Решение:** В API только агрегаты/группы/тренеры; URL считается полусекретным; см. Security.md.
- **Последствия:** Утечка URL = утечка операционных агрегатов; при росте требований — отдельный ADR на auth.

## ADR-004 — Разные определения conv1to5 (totals vs byTrainer)

- **Дата:** 2026-08-01
- **Статус:** Accepted (осознанный компромисс)
- **Контекст:** Исторически totals = weighted по головам, trainer = среднее % групп.
- **Решение:** Оставить как есть; документировать в ApiContract; не «выравнивать» молча.
- **Последствия:** Цифры на карточках могут расходиться с ожиданиями; смена — только новым полем + ADR.

## ADR-005 — Код GAS в том же git-репозитории через clasp

- **Дата:** 2026-08-01
- **Статус:** Accepted
- **Контекст:** Работа из Cursor, деплой UI из GitHub, скрипт раньше жил только в Google.
- **Решение:** Каталог `apps-script/` + clasp; UI по-прежнему через Netlify←git.
- **Последствия:** Нужна дисциплина `clasp push`/`deploy`; не коммитить credentials.

## ADR-006 — Документация и rules как защита от долга

- **Дата:** 2026-08-01
- **Статус:** Accepted
- **Контекст:** Переезд с Cloud Code; риск потери контекста.
- **Решение:** Обязательный пакет docs + `.cursor/rules/00-project.mdc`; контракт и ADR обновляются вместе с кодом.
- **Последствия:** Чуть больше работы на PR; меньше тихих breaking changes.

## ADR-010 — Кэш API и локальный stale-while-revalidate

- **Дата:** 2026-08-01
- **Статус:** Accepted
- **Контекст:** `/exec` ~2.7с+ на каждый запрос; UI долго на «Загрузка…».
- **Решение:** `CacheService` 300с в `doGet`; `?refresh=1` для кнопки «Обновить»; UI сразу рисует последний JSON из `localStorage`, затем обновляет в фоне.
- **Последствия:** Данные могут отставать до 5 минут без force-refresh; кнопка «Обновить» всегда свежий расчёт.

## ADR-009 — Явность периода и иерархия типографики

- **Дата:** 2026-08-01
- **Статус:** Accepted
- **Контекст:** KPI за весь период читались как «текущий месяц», потому что дельты были подписаны «к Июню».
- **Решение:** Баннер области данных; scope на каждой KPI-карточке; двухстрочные дельты (число + пояснение); шкала `--fs-*` для иерархии во всём UI.
- **Последствия:** Чуть больше текста на обзоре; зато меньше ложных выводов по цифрам.

## ADR-008 — Deep-link, CSV, прозрачность updatedAt

- **Дата:** 2026-08-01
- **Статус:** Accepted
- **Контекст:** Нужен шаринг карточек, выгрузка в Excel и понятная свежесть данных; карточка тренера не показывала часть уже доступных полей API.
- **Решение:** Клиентские query-параметры `period/trainer/month/tab`; CSV из текущей вкладки; `updatedAt` в шапке; расширить detail тренера (day1→итог, conv2/conv3). Без изменений GAS.
- **Последствия:** Shareable URL зависит от точного имени тренера/месяца; CSV — только агрегаты текущего view.

## ADR-007 — Операционный контроль (schemaVersion 2)

- **Дата:** 2026-08-01
- **Статус:** Accepted
- **Контекст:** Нужны фильтр периода, MoM, явные формулы конверсии и отсев по месяцам/тренерам без ломки старых полей.
- **Решение:**
  - `schemaVersion: 2`, блок `metrics` с порогами бейджей и планом.
  - Добавить `byTrainer.conv1to5Weighted` (final/day1); сохранить `conv1to5` как среднее % групп.
  - Расширить `byMonth` полями отсева и сумм.
  - UI: фильтр месяца (клиентская агрегация из `groups`), дельты к предыдущему месяцу, легенда порогов, таблица отсева по месяцам.
- **Последствия:** UI предпочитает взвешенную конверсию для сравнения; при фильтре периода `notGathered` недоступен (нет разбивки в API). Состав valid по «распалась» уточнён в ADR-011.
