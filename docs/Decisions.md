## ADR-023 — Уход кандидатов из «Регистрации уволенных» (schemaVersion 10)

- **Дата:** 2026-11-26
- **Статус:** Accepted
- **Контекст:** Руководству нужна обратная связь по ушедшим кандидатам: на какой день обучения уходят, почему, кто инициатор, у каких тренеров. Данные — во втором листе книги («Регистрация уволенных», Google-форма, 665 строк с 31.07 на 26.11). Группу из формы надёжно не определить, форму заполняют с опозданием. В причине ≈70% — пункт выпадающего списка, ≈30% — свободный текст тренера («не явился после распределения», «вышла без ОС»…), и это самые частые случаи.
- **Решение:**
  - Отдельный блок `dismissals` в JSON; с основными метриками (totals, воронка, TQI) **не смешивается**.
  - Раскладка причины — в GAS (единый источник истины): пункт списка → своя причина; свободный текст → правила по ключевым словам, включая отдельную категорию «Не вышли / ушли без ОС». Исходный текст наружу не отдаётся (там бывают имена кандидатов).
  - Отдаём справочники + компактные кортежи строк (~20KB на 665 строк), а UI считает разрезы (день × причина, день × инициатор, тренер, месяц) — как недели в ADR-020. Так фильтры месяца и тренера работают без новых запросов и без дубля формул: формул тут нет, только подсчёт.
  - Период — по дате старта группы (не по отметке времени). Тренер склеивается с «Контроль штата» той же `trainerMatchKey`.
  - Ошибка чтения листа не валит дашборд: `dismissals.ok=false`, UI показывает заглушку.
  - Ответ стал > 100KB (лимит Script Cache на ключ) — кэш `doGet` хранит JSON частями (`cachePutChunked` / `cacheGetChunked`, `putAll` / `getAll`); недостающий кусок → пересчёт.
  - UI: вкладка «Уход кандидатов» (акцент на день ухода: столбики по дням с разбивкой по причинам/инициатору, автовыводы, тепловая таблица «причина × день» со всеми причинами, инициатор по дням, тренеры, месяцы старта, фильтр тренера, CSV), блок «Уход кандидатов: когда и почему» в «Обзоре» (дни + полный список причин с %), блок в карточке тренера.
- **Последствия:** Новая формулировка в форме может попасть в «Другое» — правила дополняются в `DISMISSAL_TEXT_RULES` + DataModel. Цифры реестра ≠ «Ушли сами / отказали» основного листа (разные учёты) — в UI это подписано. Сверка «сколько ушло по основному листу vs сколько зарегистрировано» — отдельная идея (Ideas).
- **Дополнение (26.11):** записи формы привязываются к группам в UI — тот же тренер (фамилия + имя) и дата старта группы; точное совпадение у 96% записей, ещё ~2% — ближайшая группа тренера в пределах 3 дней (тренер ошибся датой), несобравшиеся группы не берём. Так в карточке группы на вкладке недель и в карточке группы видно «почему ушли». Если по таблице ушло больше, чем записей в форме (допуск 2, «не пришёл после распределения» не считаем — основной лист его отсевом не считает), показываем подсказку; проверка включается с первой группы, где в форме 3+ записи (начало реестра). API не меняется.

## ADR-022 — Колонки листа ищем по заголовкам, а не по буквам (schemaVersion 9)

- **Дата:** 2026-11-18
- **Статус:** Accepted
- **Контекст:** В листе «Контроль штата обучения» добавили колонки 4-го дня и «на выход» (P–S), итог переехал из N в T, 3-й день — из P в N, комментарий — из R в V. Скрипт читал по фиксированным индексам `A:R` — прод сразу начал отдавать неверные цифры (итог = 3-й день, «не собралось/распалось» = 0, конверсия 36,6% вместо ~27,6%).
- **Решение:**
  - `readSourceRows()` находит строки заголовков («Месяц, группа» в A, повторяются над блоками месяцев), сопоставляет поля по тексту заголовков (`HEADER_PATTERNS`) и раскладывает каждую строку во внутренний порядок `COL`. Остальной расчёт не меняется. Ширина чтения — `getLastColumn()`.
  - Обязательные колонки (`REQUIRED_COLUMNS`) не нашлись → `/exec` отвечает `{ error }`, UI показывает текст ошибки. Неверные цифры хуже, чем явная ошибка.
  - Новые колонки отдаются в `groups[]`: `day4Start`, `conv4`, `exitCount`, `exitPct`; пусто у старых групп → `null` (не 0). В UI пока не выводятся. По словам владельца (18.11): «Количество людей на выход» / «% на выход» — финальная сверочная копия итога, сотрудники дозаполняют её после выхода группы; итог для расчётов по-прежнему «Сколько людей на выход группы на линию». Кандидат на вывод — только 4-й день.
- **Последствия:** Перестановка/вставка колонок больше не ломает дашборд; переименование заголовка — ломает явно, с текстом ошибки. Кэш `dashboard_json_v9`. Проверка: по старым группам все поля совпали с ответом API от 16.11 (до перестройки листа).

## ADR-021 — Комментарий группы и «не собралась» в данных (schemaVersion 8)

- **Дата:** 2026-11-16
- **Статус:** Accepted
- **Контекст:** В колонке R владелец проставил тип группы («1-ый уровень», «Force Group», «Сервисная») — его нужно видеть на дашборде. «Не собравшиеся» группы должны быть видны в общей статистике. Скрипт узнавал только точные «не собралась» / «распалась»: 4 группы «не набралась» (июль–август, нули) считались проведёнными, «расформирована» (Орлова, авг.) — обычной группой.
- **Решение:**
  - Синонимы статусов (`groupStatusFromComment`): «не собралась» = «не набралась» = «не состоялась» → вне расчёта; «распалась» = «расформирована» → valid с меткой. Остальной текст R — тип группы, на расчёт не влияет.
  - «Не собралась» — **отдельная цифра**, не старт: в «Всего групп / стартовало», воронку, конверсию, выход/группу и TQI не входит (людей не было, тренер не виноват). Показывается везде: обзор, месяцы (`byMonth.notGathered`), тренер (`byTrainer.notGathered`), неделя (карточка «Группа не собралась»).
  - `groups[]` содержит и такие группы с `notGathered: true` — UI исключает их через `validGroupsOf()`.
  - `groups[].comment` — колонка R как есть (≤120 симв.). Решение владельца: ссылка внутренняя, регистрацию не вводим, в R нет личных данных (Security).
  - UI: тип группы — метка на карточке недели, колонка «Тип» в таблицах, фильтр «Тип группы» на вкладке недель, комментарий в CSV.
- **Последствия:** Цифры прошлых месяцев меняются (становятся верными): старты −4 за июль–август, распавшихся +1, выход на группу растёт. Порядок выката: UI → GAS (старый UI посчитал бы «не собралась» группами «в обучении»). Тренер, у которого в области только несобравшиеся группы, в `byTrainer` не появляется. Если в одной ячейке и тип, и статус — показывается статус.

## ADR-020 — Вкладка «По неделям»: два события, без изменения API

- **Дата:** 2026-11-16
- **Статус:** Accepted
- **Контекст:** Нужна понедельная отчётность «что произошло за неделю» рядом с обзором, тренерами и месяцами. Обучение идёт ~5 рабочих дней, поэтому 54% групп (91 из 167 на 16.11) стартуют в одну календарную неделю, а выходят на линию в следующую (старт в четверг → выход в среду).
- **Решение:**
  - Неделя = календарная пн–вс; ключ — дата понедельника `yyyy-MM-dd`.
  - **Старт** группы засчитывается в неделю `startDate`; **итоги** (1-й день → итог, отсев, конверсия, распад) — в неделю `lineDate` и только по законченным (`completed`, ADR-014). Каждая цифра считается ровно один раз.
  - **Идущие группы недели** (стартовали или выходят на этой неделе, D ещё не наступила) видны отдельно и помечены «предварительно»: штриховая часть воронки (1-й / 2-й / 3-й день по уже внесённому), колонки 1-й / 2-й / 3-й день и отсев серым в «Группах недели», колонка «Идут сейчас» у тренеров. В KPI, конверсию и тренд они не входят — правило ADR-014 сохраняется.
  - Считает только UI из уже отдаваемого `groups[]` (presentation-aggregate, как фильтр месяца в ADR-007). GAS, `schemaVersion`, ApiContract и deployment не меняются.
  - Фильтр месяца на вкладке недель не действует и скрыт; deep-link `?tab=weeks&week=<понедельник>`; CSV — все недели + группы выбранной.
  - TQI по неделе не считаем: на 1–2 группах рейтинг не показателен; в «Тренерах недели» — сырые цифры.
  - **Простой вид для неспециалистов** (порядок экрана): «Коротко о неделе» (готовые фразы) → карточки групп «Стартовали на этой неделе» и «Начали раньше — выходят на линию на этой неделе» → 4 главные цифры (стартовало, вышли на линию, дошли до линии %, отсеялись). Воронка, таблицы, тренеры, тренд и список недель — в раскрывающемся блоке «Подробная аналитика недели».
  - **Статус группы «сегодня»** на карточке — только подпись, в расчёты не идёт: учебные дни = рабочие пн–пт от `startDate` (1-й день) до дня перед `lineDate`; «Сегодня N-й день обучения из M», «Сегодня выход на линию», «Старт завтра / пн 23.11», «Выходные», «Вышла на линию dd.mm», «Распалась». Дата «сегодня» — по часам браузера.
  - Пустые недели подписаны «групп не было» (в списке недель и в таблице).
  - Клик по тренеру на вкладке недель открывает карточку: сверху «Неделя тренера» (сводка + карточки его групп недели), ниже общий обзор **за весь период** — скрытый фильтр месяца здесь не действует.
  - В карточке тренера (с любой вкладки) — переключатель «Период»: весь период / месяц, где у тренера были группы (по умолчанию — фильтр месяца сверху, с вкладки недель — весь период). Клик по группе (таблица «Группы тренера» или карточка недели внутри) открывает **карточку группы**: дни 1→2→3→линия, конверсии, отсев с % от 1-го дня, статус «сегодня», комментарий; «← К тренеру» возвращает с тем же периодом. Только представление, расчёты не меняются.
- **Последствия:** Пустые недели (нет ни стартов, ни выходов) показываются явно. Журнал ОС по неделям не режется: в журнале нет надёжной даты на строку (даты — заголовки блоков без года); если понадобится — отдельный ADR и правка GAS/контракта. Отсев по календарным дням недели невозможен: в листе отсев — одно число на группу.

## ADR-019 — Уволенные остаются в цифрах, с меткой

- **Дата:** 2026-09-02
- **Статус:** Accepted
- **Контекст:** ADR-018 прятал уволенных из рейтинга и линии. Это искажало средние, места и вклад оставшихся.
- **Решение:** Список `DEPARTED_TRAINERS` (Селиванова Олеся, Вовчак Лариса, Фишер Артем). Они в `byTrainer`, TQI и журнале ОС как все. Поле `departed` + UI «(Уволен)» в рейтинге, линии, распавшихся, карточке. Скрытие отменено.
- **Последствия:** Кэш `dashboard_json_v7d`. Новый уволенный — строка в списке.

## ADR-018 — Уволенные вне рейтинга и оценки линии

- **Дата:** 2026-09-02
- **Статус:** Superseded by ADR-019
- **Контекст:** Селиванова Олеся и Вовчак Лариса уволены, но остаются в «Контроль штата» и журнале ОС. В рабочем рейтинге и оценке линии они не нужны; историю выпусков компании стирать нельзя.
- **Решение:** Список `EXCLUDED_TRAINERS` в GAS. Нет в `byTrainer`, рейтинге, таблице линии и средней компании по ОС. Группы в `groups` / totals / месяцы. Склейка по `trainerMatchKey`. UI читает `metrics.excludedTrainers`, чтобы фильтр месяца не вернул их.
- **Последствия:** Искажает рейтинг и средние по линии. Заменено меткой без исключения (ADR-019).

## ADR-017 — Склейка имён: ё = е

- **Дата:** 2026-09-02
- **Статус:** Accepted
- **Контекст:** В «Контроль штата» канон с «ё» (Дегтярёва). В журнале ОС супервайзоры выбирают тренера из списка без «ё» — другую букву поставить нельзя. Точное сравнение ключа оставляло оценки в `unmatched`.
- **Решение:** В `trainerMatchKey` сводить `ё`/`Ё` к `е`. Экранное имя не менять. Группы обучения по разным написаниям не сливать.
- **Последствия:** Два разных человека «Ё» vs «Е» склеятся; при штате из списка ОС это приемлемо. Кэш `dashboard_json_v7e`.

## ADR-016 — TQI v3: оценка после линии в рейтинге (schemaVersion 7)

- **Дата:** 2026-09-02
- **Статус:** Accepted
- **Контекст:** Журнал ОС даёт факт подготовки на линии (колонка M, 1–5). TQI v2 смотрел только воронку обучения. Нужен общий балл «выпустили и как оценили», без доминирования журнала и без штрафа за 1 оценку.
- **Решение:**
  - **TQI v3** (`metrics.rankScore: tqi_v3`): 40% quality воронки + **5% line** (балл 1–5) + **5% skills** (доля «да» скрипт/возражения/CRM) + 15% reliability + 20% contribution + 10% yield + 5% stability.
  - `line` = `(avgScore / 5) × 100`. Своя средняя, если `scored ≥ 2`. Иначе средняя компании. Нет журнала — 60.
  - `skills` = среднее `scriptYesRate`, `objectionsYesRate`, `crmYesRate` (только заполненные да/нет; пусто ≠ нет). Свои доли, если сумма filled ≥ 2. Иначе средняя компании. Нет журнала — 80.
  - Фильтр месяца не режет линию и навыки.
  - `schemaVersion: 7`, кэш `dashboard_json_v7`; `scoreParts.line` / `lineFill` / `skills` / `skillsFill`.
  - UI полный рейтинг и вкладка тренеров: колонка **«Оценка кандидатов»** = `scoreParts.skills` (скрипт / возражения / CRM).
- **Последствия:** `score` и места несравнимы с v2. GAS считает TQI после склейки `lineReview`.

## ADR-015 — Оценка после линии из журнала ОС (schemaVersion 6)

- **Дата:** 2026-09-02
- **Статус:** Accepted
- **Контекст:** Есть отдельная книга «Выход на линию — ОС»: супервайзоры ставят подготовку 1–5 и да/нет по скрипту/возражениям/CRM. Прогноз в колонке — гуманитарный текст, не факт выхода.
- **Решение:**
  - Читать лист `2026` второй книги по ID (`SpreadsheetApp.openById`), executeAs по-прежнему деплоер.
  - В JSON только агрегаты `lineReview` (средняя 1–5 с десятыми, доли «да»). Без ФИО, прогноза и комментариев.
  - Склейка с обучением: фамилия + имя, префикс «Тренер» срезается; в UI имя как в «Контроль штата» (позже ADR-017: `ё`=`е`).
  - TQI **на тот момент не меняли** (позже ADR-016 / TQI v3). Фильтр месяца журнал ОС не режет (в строках нет стабильной даты группы).
  - Нет доступа ко второй книге → обучение отдаём, `lineReview.ok: false`.
- **Последствия:** Нужен «Читатель» на журнал ОС у аккаунта деплоера; первый запуск может запросить новые права Sheets. `schemaVersion: 6`, кэш `dashboard_json_v6`.

## ADR-014 — Outcome только по законченным группам (дата D ≤ сегодня)

- **Дата:** 2026-08-21
- **Статус:** Accepted
- **Контекст:** C и D заполняются при создании группы (плановые даты). Карточка «вышло на линию» и конверсии смешивали закрытый поток с ещё идущим обучением.
- **Решение:**
  - Законченная: `lineDate ≤ сегодня` (таймзона скрипта) **или** «распалась».
  - `totals.groups` / `byTrainer.groups` / `byMonth.groups` — все старты valid (в т.ч. в обучении).
  - Воронка, day1, отсев, `finalCount`, conv, yield, TQI — только законченные.
  - `schemaVersion: 5`, кэш `dashboard_json_v5`; поля `completed`, `lineDate`, `groupsCompleted`, `groupsInProgress`.
- **Последствия:** Текущий месяц «догоняет» по мере наступления D. Сравнение v4/v5 по выходу и 1→5 некорректно без оговорки.

## ADR-013 — TQI v2: гибрид качества и вклада + полный рейтинг

- **Дата:** 2026-08-01
- **Статус:** Superseded by ADR-016 (формула `score`; поля тренера те же)
- **Контекст:** TQI v1 почти совпадал с % 1→5; не учитывал «стартовали → остались» в абсолюте и завышал малые выборки (см. анализ fairness).
- **Решение:**
  - **TQI v2** (`metrics.rankScore: tqi_v2`, `schemaVersion: 4`): 50% quality (mix 1→5/2→5/3→5) + 15% reliability(log day1) + 20% contribution (доля итоговых выходов, 25%=100) + 10% yield/группу vs avg + 5% stability.
  - Поля тренера: `rank`, `leftRate`, `yieldPerGroup`, `contributionShare`, `scoreParts`.
  - Totals: `leftSelfRate`, `yieldPerGroup`, …
  - UI: полный рейтинг всех тренеров, блоки сильных/слабых сторон, расширенные KPI; не только top-4.
- **Последствия:** Числа `score` несравнимы с v1; кэш `dashboard_json_v4`.

## ADR-012 — Составной рейтинг тренеров (TQI)

- **Дата:** 2026-08-01
- **Статус:** Superseded by ADR-013
- **Контекст:** Топ «лучших/требуют внимания» смотрел только на конверсию 1→5 и игнорировал mid-funnel, отсев и распад групп.
- **Решение:** Индекс **TQI** v1 (`byTrainer.score`, 0–100): 45% conv1to5Weighted + 15% conv2 + 10% conv3 + 20% удержание + 5% отказы + 5% стабильность.
- **Последствия:** Заменён гибридом TQI v2 (ADR-013).

## ADR-011 — «Распалась» в valid + метка; «не собралась» вне расчёта

- **Дата:** 2026-08-01
- **Статус:** Accepted
- **Контекст:** Счётчик групп у тренера расходился с листом: «распалась» исключалась из valid вместе с «не собралась», хотя старт и воронка уже были.
- **Решение:**
  - «не собралась» — по-прежнему вне valid (`notGathered`).
  - «распалась» — в valid, в totals/byTrainer/byMonth/воронку; флаг `groups[].fellApart`; счётчики и `fellApartConv1to5` / `fellApartShare`.
  - `schemaVersion: 3`, ключ кэша `dashboard_json_v3`.
  - UI: KPI «Распалось», бейдж, блоки аналитики по тренерам/месяцам, список групп в карточке тренера.
- **Последствия:** Число `totals.groups` и конверсии вырастут относительно v2 (туда войдут распавшиеся). Сравнивать периоды до/после выкладки осторожно.

## ADR-001 — Статический UI + Apps Script JSON API

- **Дата:** 2026-08-01
- **Статус:** Accepted
- **Контекст:** Нужен внешний дашборд поверх Google Sheets без тяжёлого backend.
- **Решение:** Данные агрегирует Apps Script; UI — статический `index.html` на Netlify; связь через публичный Web App `/exec`.
- **Последствия:** Простота и скорость; нет серверного auth; контракт JSON критичен; два пайплайна деплоя (git и clasp).

## ADR-002 — Единая функция агрегации

- **Дата:** 2026-08-01
- **Статус:** Accepted
- **Контекст:** Нужны и лист «Дашборд», и веб-JSON.
- **Решение:** `collectDashboardData()` — единственный расчёт; `buildDashboard` и `doGet` только потребители.
- **Последствия:** Менять формулы в одном месте; запрещено дублировать бизнес-логику в UI без причины.

## ADR-003 — Публичный доступ к `/exec` без ПДн учеников

- **Дата:** 2026-08-01
- **Статус:** Accepted
- **Контекст:** Web App с доступом «Anyone» упрощает fetch из статики.
- **Решение:** В API только агрегаты/группы/тренеры; URL считается полусекретным; см. Security.md.
- **Последствия:** Утечка URL = утечка операционных агрегатов; при росте требований — отдельный ADR на auth.

## ADR-004 — Разные определения conv1to5 (totals vs byTrainer)

- **Дата:** 2026-08-01
- **Статус:** Accepted (осознанный компромисс)
- **Контекст:** Исторически totals = weighted по головам, trainer = среднее % групп.
- **Решение:** Оставить как есть; документировать в ApiContract; не «выравнивать» молча.
- **Последствия:** Цифры на карточках могут расходиться с ожиданиями; смена — только новым полем + ADR.

## ADR-005 — Код GAS в том же git-репозитории через clasp

- **Дата:** 2026-08-01
- **Статус:** Accepted
- **Контекст:** Работа из Cursor, деплой UI из GitHub, скрипт раньше жил только в Google.
- **Решение:** Каталог `apps-script/` + clasp; UI по-прежнему через Netlify←git.
- **Последствия:** Нужна дисциплина `clasp push`/`deploy`; не коммитить credentials.

## ADR-006 — Документация и rules как защита от долга

- **Дата:** 2026-08-01
- **Статус:** Accepted

## ADR-010 — Кэш API и локальный stale-while-revalidate

- **Дата:** 2026-08-01
- **Статус:** Accepted
- **Контекст:** `/exec` ~2.7с+ на каждый запрос; UI долго на «Загрузка…».
- **Решение:** `CacheService` 300с в `doGet`; `?refresh=1` для кнопки «Обновить»; UI сразу рисует последний JSON из `localStorage`, затем обновляет в фоне.
- **Последствия:** Данные могут отставать до 5 минут без force-refresh; кнопка «Обновить» всегда свежий расчёт.

## ADR-009 — Явность периода и иерархия типографики

- **Дата:** 2026-08-01
- **Статус:** Accepted
- **Контекст:** KPI за весь период читались как «текущий месяц», потому что дельты были подписаны «к Июню».
- **Решение:** Баннер области данных; scope на каждой KPI-карточке; двухстрочные дельты (число + пояснение); шкала `--fs-*` для иерархии во всём UI.
- **Последствия:** Чуть больше текста на обзоре; зато меньше ложных выводов по цифрам.

## ADR-008 — Deep-link, CSV, прозрачность updatedAt

- **Дата:** 2026-08-01
- **Статус:** Accepted
- **Контекст:** Нужен шаринг карточек, выгрузка в Excel и понятная свежесть данных; карточка тренера не показывала часть уже доступных полей API.
- **Решение:** Клиентские query-параметры `period/trainer/month/tab`; CSV из текущей вкладки; `updatedAt` в шапке; расширить detail тренера (day1→итог, conv2/conv3). Без изменений GAS.
- **Последствия:** Shareable URL зависит от точного имени тренера/месяца; CSV — только агрегаты текущего view.

## ADR-007 — Операционный контроль (schemaVersion 2)

- **Дата:** 2026-08-01
- **Статус:** Accepted
- **Контекст:** Нужны фильтр периода, MoM, явные формулы конверсии и отсев по месяцам/тренерам без ломки старых полей.
- **Решение:**
  - `schemaVersion: 2`, блок `metrics` с порогами бейджей и планом.
  - Добавить `byTrainer.conv1to5Weighted` (final/day1); сохранить `conv1to5` как среднее % групп.
  - Расширить `byMonth` полями отсева и сумм.
  - UI: фильтр месяца (клиентская агрегация из `groups`), дельты к предыдущему месяцу, легенда порогов, таблица отсева по месяцам.
- **Последствия:** UI предпочитает взвешенную конверсию для сравнения; при фильтре периода `notGathered` недоступен (нет разбивки в API). Состав valid по «распалась» уточнён в ADR-011.
